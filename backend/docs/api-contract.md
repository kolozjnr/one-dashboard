# HTTP API conventions

The API is rooted at `/api/v1`. Successful JSON responses use:

```json
{
  "success": true,
  "data": {},
  "meta": { "requestId": "uuid" }
}
```

Errors use a stable envelope and never include stack traces:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request could not be processed",
    "details": [{ "field": "email", "message": "email must be an email" }]
  },
  "meta": { "requestId": "uuid" }
}
```

DTOs are validated by the global `ValidationPipe` with transformation, unknown-field rejection, and a normalized validation error. Controllers must bind query parameters to validated DTOs and use `ParseUUIDPipe` (or an equivalent domain pipe) for UUID path parameters. Use `createImageUploadPipe()` for image uploads; it rejects files over 5 MiB or files that are not PNG, JPEG, or WebP. Webhook routes must validate provider signatures against the raw request body before processing anything; the enabled ones are `POST /api/v1/payments/webhooks/:provider` (Paystack, Flutterwave, Stripe), whose adapters parse provider-specific payloads into one normalized event.

`x-request-id` is generated by the API, returned in `meta`, and used in request/error logs. Request logs exclude query strings and request bodies to avoid recording credentials or personal data. Production error responses suppress internal exception messages and stack traces.

## Authorization

`CsrfGuard`, `AccessTokenGuard`, and `PermissionsGuard` run globally (in that order). Controllers declare requirements with `@RequireWorkspacePermission(s)` or `@RequireAdminPermission(s)`; the guard resolves them from metadata and never from client input. Workspace scope comes from the `:workspaceId` route parameter and is checked against database membership and role grants on every request — the frontend only renders hints (`GET /workspaces/:workspaceId/permissions` and the `platform` field on `auth/me`) and is never trusted for access decisions.

Subscriber (workspace) permissions and platform (admin) permissions are separate systems: `admin.*` keys are rejected in workspace roles, `workspace.transfer_ownership` is owner-reserved, actors cannot grant permissions they lack themselves, and only Super Admins can grant the `super-admin` role (never to themselves). Role and permission grants are recorded in `AuditLog`. Platform admin routes live under `/api/v1/admin/*` and require an `AdminMembership` role with the matching `admin.*` permission.

## Plans, subscriptions and entitlements

`GET /api/v1/plans` is the public pricing catalog; every limit comes from `SubscriptionPlan` rows in the database. Workspace subscription lifecycle is at `/api/v1/workspaces/:workspaceId/subscription*` (requires `workspace.view` / `workspace.billing`); plan administration and subscription/payment overrides are under `/api/v1/admin/plans*`, `/api/v1/admin/subscriptions*`, and `/api/v1/admin/payments*` (requires the matching `admin.*` permission).

`EntitlementsService` is the single source of truth for plan limits — `canConnectAccount()`, `canInviteMember()`, `canCreateWebsite()`, `canGenerateReport()`, `canUseAI()`, `canAccessFeature()` plus `assert*`/`consumeUsage` variants. Controllers must call it instead of reading limits from request bodies or duplicating plan checks; monthly report/AI usage is metered through `UsageCounter` rows scoped to the workspace and UTC month.

## Payments and payment gateways

Payment processing is provider-independent: controllers speak only to `PaymentsService`, `PaymentGatewaysService` and `PaymentProcessingService`, and only the adapters in `src/modules/payments/gateways/` know provider names. A gateway becomes `ACTIVE` only after every required credential **and** configuration value is supplied; secrets are AES-256-GCM encrypted (`PaymentGateway.credentialsCiphertext`, key from `PAYMENT_ENCRYPTION_KEY`, derived from `JWT_SECRET` otherwise) and are never returned by any read path.

Workspace payment routes (`workspace.view` to read, `workspace.billing` to act) live under `/api/v1/workspaces/:workspaceId/payments`:

| Route | Purpose |
| --- | --- |
| `POST /payments` | Initializes a checkout: mints a unique `reference`, stores a `PENDING` payment, calls the gateway, returns `checkoutUrl`. Send an optional `Idempotency-Key` header to make retries safe. |
| `GET /payments` | Paginated transaction history (`?status=` filter). |
| `GET /payments/:paymentId` | Payment details with its `PaymentEvent` and `PaymentRefund` rows; `?refresh=true` re-reads the gateway without changing state. |
| `POST /payments/:paymentId/verify` | The **only** path that can settle a payment: fetches the transaction from the gateway's verification endpoint, compares reference, amount, currency and association, then applies the outcome and any subscription transition in one database transaction. |
| `POST /payments/:paymentId/cancel` | Cancels a `PENDING` checkout (never grants entitlement, so a tenant-declared intent is sufficient). |

A successful redirect is never proof of payment: no route trusts query parameters, `success_url` values, or client-declared amounts. Settlement comes from the gateway verification endpoint, a signature-verified webhook, or a reference plus amount/currency comparison — mismatches are rejected, logged as `PaymentEvent`/`AuditLog` entries, and never move money state.

Webhooks: `POST /api/v1/payments/webhooks/:provider` is public (`@Public()`, `@SkipCsrf()`, `@SkipThrottle()`) and requires the raw request body (`rawBody: true` at bootstrap). Signatures are checked constant-time against the exact bytes (Paystack `x-paystack-signature` HMAC-SHA512, Flutterwave `verif-hash`, Stripe `stripe-signature` HMAC-SHA256 with timestamp tolerance). Responses: `401` invalid signature, `409` gateway not configured, `400` unparseable body, otherwise `200` with the event status (`PROCESSED`, `DUPLICATE`, `IGNORED`, `REJECTED`). Every delivery is stored in `PaymentEvent` keyed by `provider:eventId`, so redeliveries are database-level no-ops; `FAILED` rows may be replayed by the provider.

Admin payment routes (platform `admin.*` permissions) are under `/api/v1/admin`: `GET/PUT/DELETE /admin/payment-gateways*` and `POST /admin/payment-gateways/:provider/test` (`admin.payments.view`/`manage`), `POST /admin/payments/:paymentId/verify` (`admin.payments.manage`), `POST /admin/payments/:paymentId/refund` (`admin.payments.refund`), and `POST /admin/subscriptions/:subscriptionId/activate` (`admin.subscriptions.activate`). Manual activation requires **exactly one** of `paymentReference` or `evidence` (amount, currency, method, optional reference/notes), a `reason` of at least 10 characters, and `confirm: true`; a reference must resolve to that subscription's payment and must be `SUCCEEDED` (a pending gateway payment is verified first, failed/canceled/refunded payments are refused), and evidence must match the plan's charge amount and currency. The administrator identity, reason, evidence and payment id are written to `AuditLog` and to the `SubscriptionEvent` in the same transaction — there is no path that silently overrides a failed or unverified payment.

On a verified successful payment for a pending subscription, one transaction marks the payment `SUCCEEDED`, activates the subscription (start/expiry dates), snapshots workspace entitlements into the subscription event, writes the audit entry, and afterwards queues the confirmation notification on the `notifications` BullMQ queue (in-app `Notification` row plus best-effort email). Full refunds of a gateway payment suspend the subscription; partial refunds only reduce the refunded total.

The confirmation queue is intentionally best-effort: the in-app `Notification` row is written first and is the durable record, so a broker problem never fails a payment (the enqueue is caught and logged as a warning). BullMQ requires **Redis ≥ 5.0** for the `notifications` queue and its worker; on older brokers the API still runs and in-app confirmations still appear, but the queued email leg stays undelivered until the broker is upgraded.

## Integrations (Meta OAuth)

Controllers speak only to `IntegrationsService`; only the adapters in `src/modules/integrations/` know Meta host names, endpoint paths or scope names. Instagram and Facebook are separate API products with **separate permission sets** (`instagram_business_*` vs `pages_show_list`/`pages_read_engagement`/`read_insights`) that are never combined — see `docs/meta-integrations.md` for the verified flows, account-type eligibility and metric availability rules.

| Route | Permission | Purpose |
| --- | --- | --- |
| `GET /workspaces/:workspaceId/integrations` | `integrations.view` | Connected Meta accounts (status, granted scopes, token expiry, linked IG account) plus which products are configured. Never returns tokens. |
| `POST /workspaces/:workspaceId/integrations/authorize` | `integrations.connect` | Body `{ "product": "instagram" \| "facebook" }`; returns the Meta authorization URL carrying a signed `state`. |
| `GET /integrations/meta/callback` | `@Public()` | Meta's redirect target, reached via the Next.js route `{APP_BASE_URL}/auth/meta/callback`. Validates the signed state, exchanges the code, upgrades to a long-lived token, seals it, discovers accounts (professional IG account / one row per Facebook Page) and returns the page to redirect to. The browser never sees a token. |
| `GET /workspaces/:workspaceId/integrations/:accountId/insights` | `analytics.view` | Fetches supported metrics for the range (`?since&until&metrics`, clamped to 90 days), persists successes to `AnalyticsSnapshot` + `AccountMetricCapability` and a `SyncJob`, and reports per-metric `unsupported` reasons instead of failing the sync. |
| `POST /workspaces/:workspaceId/integrations/:accountId/disconnect` | `integrations.disconnect` | Marks `DISCONNECTED`, soft-deletes the row, **destroys the ciphertext** and writes an audit entry. |

Tokens are AES-256-GCM sealed (`INTEGRATIONS_ENCRYPTION_KEY`, falling back to `PAYMENT_ENCRYPTION_KEY`/`JWT_SECRET` derivation) in `ConnectedAccount.credentialsCiphertext`, refreshed where Meta supports it (Instagram `ig_refresh_token`, Facebook `fb_exchange_token`), and never logged — the Graph client redacts token/secret material from every error message. Revoked permissions move the account to `NEEDS_REAUTH`; connect/disconnect actions are recorded in `AuditLog`.

`GET /api/v1/health` returns the app version and only `ok`/`unavailable` dependency states. `/docs` serves the generated OpenAPI document and UI.
